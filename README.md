# Booking Desk

[![CI](https://github.com/fxm-inteligence/Engine-booking-desk/actions/workflows/build.yml/badge.svg)](https://github.com/fxm-inteligence/Engine-booking-desk/actions/workflows/build.yml)

Образец большого проекта, сгенерированного в FxM Engine: **правила записи заданы блоками бизнес-логики на холсте** (проверка слотов, переходы статусов, целостность, уведомления), а не написаны руками. Онлайн-запись клиентов для сервисного бизнеса (салон, барбершоп, студия). Он показывает, что Engine собирает не отдельные куски, а все части продукта сразу, и даёт оценить код до регистрации и оплаты.

Это **каркас, а не готовый продукт**. Раздел «Чего здесь нет» ниже стоит прочитать до того, как вы начнёте сравнивать с готовыми сервисами записи.

## Что внутри

Все восемь разделов Engine в одном репозитории:

| Часть | Папка | Технологии | Что это |
|---|---|---|---|
| База данных | `database/` | Prisma, PostgreSQL | Таблицы услуг, мастеров, клиентов и записей; запись ссылается на услугу и мастера внешними ключами |
| Сервер | `backend/` | NestJS | CRUD по ресурсам `Service`, `Master`, `Client`, `Booking`, `Notice`; правила записи, вход и роли, Swagger, ограничение частоты запросов |
| Сайт | `frontend/` | React, Vite, Tailwind | Страницы: услуги, мастера, клиенты, записи (с календарём занятости), уведомления, запись, вход |
| Telegram-бот | `telegram/` | Telegraf | Команды `/start`, `/services`, `/book`, `/mybookings` и клиент для API |
| Мобильное приложение | `mobile/` | React Native, Expo | Экран «Записи на сегодня» для мастера и клиент для API |
| Приложение для компьютера | `desktop/` | Electron, Vite | Окно стойки администратора, меню, значок в трее |
| Облачные серверы | `infrastructure/` | Terraform (AWS) | Кластер ECS, контейнер сервера, управляемая база, хранилище |
| Сборка и выпуск | `.github/workflows/` | GitHub Actions | Сборка и тесты всех частей на каждый push в `main` |

## Что работает сейчас

Только то, что генератор подключает сам. Остальное — заготовки (см. следующий раздел).

- **Сервер.** Создание, чтение, изменение и удаление услуг, мастеров, клиентов и записей. **Правила записи** задают блоки бизнес-логики на холсте (`project.json`), код выпускает генератор (`booking-service.logic.ts`, `master-service.logic.ts`, `service-service.logic.ts`):
  - *Проверка слотов (Slot Check):* мастер не может иметь две пересекающиеся записи, длительность берётся из услуги (`durationMinutes`), ответ 409; отменённая запись освобождает время. **Рабочие часы салона:** пн–пт 10:00–20:00, сб 10:00–18:00, воскресенье выходной, часовой пояс `Europe/Moscow`, в праздники (1–8 января, 23 февраля, 8 марта, 1 и 9 мая, 12 июня, 4 ноября) запись не принимается; запись должна целиком уместиться в рабочее время (ответ 409 «Салон в это время закрыт»). Две записи на одно время, пришедшие одновременно, не пройдут обе (блокировка на PostgreSQL).
  - *Статусы (Status Flow):* `new → confirmed → done`, отменить можно из `new` и `confirmed`; недопустимый переход отвечает 409; каждый переход сохраняется в историю (`GET /booking-status-logs`); запись, которую не подтвердили за 24 часа, сама отменяется (таймер).
  - *Целостность (Integrity):* услугу или мастера с записями удалить нельзя (409).
  - *Лимит (Limit):* не больше трёх записей на один телефон на один день (защита публичной формы от спама).
  - *Идемпотентность:* повтор `POST /bookings` с тем же заголовком `Idempotency-Key` не создаёт вторую запись.
  - *Журнал (Audit):* кто и что менял в записях (`GET /booking-audit-logs`).
  - *Уведомления (Reaction):* новая запись и подтверждённая запись за 24 часа до начала создают запись в таблице `Notice` («новая запись», «напомнить клиенту»): это ящик уведомлений для персонала (`GET /notices`, страница `/notices`). Писем и сообщений клиенту сервер не отправляет, см. следующий раздел.
  - *Доступные маршруты:* `GET /bookings/busy` (занятое время) и `GET /bookings/:id/transitions` (в какие статусы запись может перейти сейчас), `PATCH /bookings/:id` (частичное изменение, например только статуса).

  **Вход и роли** (генерирует блок «Auth»): `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`; сервер выдаёт сессию в защищённом cookie. Регистрация всегда создаёт роль `user`: поле `role` из запроса игнорируется (проверено: `{"role":"admin"}` даёт `user`). Клиент может создать запись без входа (`POST /bookings`), услуги и мастера читаются без входа; всё остальное (изменение услуг и мастеров, список клиентов и записей) доступно только роли `admin`, остальным отвечает 401 или 403. Первого администратора назначает владелец вручную, см. быстрый старт.
- **Сайт.** Публичные страницы: «Услуги» (`/`) и «Мастера» (`/masters`) показывают таблицы с сервера; «Записаться» (`/book`) — форма с выпадающими списками «Услуга» и «Мастер» (берутся из базы), именем, телефоном и временем; статус новой записи сервер ставит сам (`new`). Страница входа `/login`. Страницы для сотрудников требуют входа (без сессии браузер уходит на `/login`): «Записи» (`/bookings`) показывает таблицу записей и календарь занятости на ближайшие 14 дней (блок «Busy Calendar», время считает сервер), «Уведомления» (`/notices`) и «Клиенты» (`/clients`) показывают таблицы; на страницах есть кнопка «Выйти» и ссылки на соседние страницы сотрудника. Статус записи в интерфейсе менять нельзя (только через API): у таблицы нет ссылки на страницу записи, поэтому кнопки статусов (блок «Status Buttons») здесь не подключены.
- **Telegram-бот.** Команда `/services` вызывает API и отвечает списком названий услуг из базы. Команды `/start`, `/book` и `/mybookings` отвечают фиксированным текстом (см. следующий раздел).
- **Мобильное приложение и десктоп.** Запускаются и показывают заготовки: экран с заголовком и кнопкой, окно с заголовком и кнопкой.

## Что проверено

- `cd backend && npm install && npm test`: **93 теста, все проходят, база данных не нужна**: тесты сервисов (создание, список, чтение, изменение, удаление, 404), разбор параметров списка и тесты, которые генератор пишет к каждому блоку логики (рабочие часы и часовые пояса, пересечения, переходы статусов, история, таймеры, журнал, лимит, идемпотентность, реакции, целостность). Тесты работают на репозитории в памяти.
- **Правила на настоящей базе** (PostgreSQL 16 в Docker, собранный сервер, 25 проверок скриптом по HTTP; скрипт в репозиторий не входит и в CI не запускается): запись в рабочее время создаётся, воскресенье, время после закрытия и праздник отвечают 409, пересекающаяся запись отвечает 409, а запись следом принимается; услуга на 90 минут занимает и второй час; четвёртая запись на один телефон в один день отвечает 409; повтор с тем же `Idempotency-Key` возвращает ту же запись; `new → done` отвечает 409, `new → confirmed` проходит; отменённая запись освобождает время; история статусов и журнал изменений ведутся; услугу и мастера с записями удалить нельзя; новые записи появляются в уведомлениях; уведомления и занятое время без входа недоступны. Таймер отмены через 24 часа и напоминание за 24 часа на живом сервере не ждались: они проверены только тестами.
- **Сайт на живом сервере:** собран (`tsc -b && vite build`), вход сотрудника ведёт на `/bookings`, на странице видны таблица и календарь занятости, страница `/notices` показывает уведомления.
- **GitHub Actions** на каждый push в `main`: собирает сайт, сервер, мобильное приложение (проверка типов), бота и десктоп, затем запускает тесты. Результат виден в значке выше и во вкладке Actions.
- **Сквозная проверка вручную в Docker** (не входит в CI): `docker compose up --build` поднимает базу, сервер и сайт; публичные маршруты отвечают 200, защищённые отвечают 401 без входа и 403 для обычного пользователя, 200 для администратора; регистрация с `role: admin` создаёт `user`; неверный пароль даёт 401; в настоящем браузере проверен весь путь: гость на `/bookings` уходит на `/login`, форма записи сохраняет запись, вход ведёт на `/bookings` с таблицей, «Выйти» снимает сессию; пересекающаяся запись у того же мастера отвечает 409, запись встык принимается (проверено на 30-минутной услуге). Смена статуса проверена только модульными тестами: обновление в API требует полного тела запроса. Команда `/services` проверена против этого сервера с подставным клиентом Telegram: бот получил услуги из базы и сформировал текст ответа. Настоящий бот с токеном BotFather не запускался.

## Чего здесь нет

Честный список, чтобы вы не нашли это сами и не разочаровались:

- **Уведомления только внутри системы.** Клиенту не уходит ни письма, ни сообщения: напоминание и «новая запись» попадают в таблицу `Notice` для персонала. Письмо клиенту не подключено, потому что ресурс (`Resource`) в Engine нельзя соединить с интеграцией почты. Мастеру в Telegram или по SMS ничего не отправляется. Оплаты нет.
- **Расписание общее для всего салона.** Рабочие часы, часовой пояс и праздники заданы одним блоком; у каждого мастера своего графика, отпуска и перерыва нет. Время в праздничные дни — российские государственные праздники, перенесённые выходные в списке не учтены. Проверка занятости читает все записи мастера (поиском по полю), она не рассчитана на миллионы записей. Если длительность услуги не нашлась (нет базы, неизвестный id), берётся 60 минут. Таймер автоотмены (24 часа) жёстко задан в блоке.
- **Занятое время виден только сотрудникам.** Маршрут `GET /bookings/busy` защищён так же, как список записей: у ресурса один переключатель публичного чтения на всю таблицу, а список записей содержит имена и телефоны. Поэтому на публичной странице записи календаря нет и клиент не видит, какое время занято, пока не отправит форму и не получит 409.
- **Статусы меняются только через API.** В интерфейсе нет кнопок «подтвердить» и «отменить»: у таблицы нет ссылки на страницу записи, а блок «Status Buttons» работает на странице одной записи.
- **Часть заготовок не подключена к API.** Команды `/book` и `/mybookings` отвечают фиксированным текстом: для записи нужен диалог (выбор услуги, мастера и времени), для «моих записей» нужно знать, кто пишет боту, а бот не умеет связать пользователя Telegram с записями. Подключать список записей к боту без этого нельзя: любой пользователь бота увидел бы чужие записи. Бот ходит только в публичные маршруты (услуги); общий ключ `API_KEY` больше не поддерживается сервером. У мобильного экрана и десктопного окна нет списка записей. Клиент для API у мобильного приложения сгенерирован (`mobile/api`), но ни к одной кнопке не привязан. У десктопа клиента для API нет.
- **Вход есть только на сайте.** Мобильное приложение и десктоп не умеют входить (экран входа не нарисован), бот не связывает Telegram с аккаунтом. Клиенты бота и мобильного всё ещё могут отправлять заголовок `x-api-key`, но сервер его больше не проверяет.
- **Роли и вход минимальны.** Две роли (`user` и `admin`), свободная регистрация (любой может создать обычную учётную запись, она ничего не открывает), нет подтверждения почты, сброса пароля и интерфейса для выдачи прав: администратора назначают SQL-командой. Токен сессии хранится в cookie, `JWT_SECRET` должен быть длинным случайным значением.
- **Тесты есть только у сервера, и они на репозитории в памяти.** У сайта, мобильного приложения, десктопа и бота тестов нет (CI их только собирает). Проверка на настоящей базе по HTTP сделана вручную скриптом, в репозиторий и CI она не входит.
- **Мобильное приложение проверено только типами**, на телефоне и в эмуляторе оно не запускалось.
- **Десктоп собирается, но окно не запускалось** и установщик (`npm run dist`) не проверялся.
- **Terraform проверен только `terraform validate`** (Terraform 1.9, провайдер AWS 5.100: «The configuration is valid»). `plan` и `apply` не запускались и к реальному аккаунту не применялись. Перед `apply` проверьте регион, образ контейнера и стоимость.
- **Сайт на React + Vite, а не на Next.js.** Десктопное приложение Engine собирается только поверх такого сайта, а в одном проекте они должны сочетаться.

## Быстрый старт: сайт, сервер и база

Нужен [Docker Desktop](https://www.docker.com/products/docker-desktop/) (бесплатный).

1. Скопируйте `backend/.env.example` в `backend/.env` и впишите в `JWT_SECRET` длинный случайный текст (подпись сессий). Без него вход не работает. При запуске по `https` поставьте `COOKIE_SECURE=true`.
2. В корне репозитория выполните:

   ```bash
   docker compose up --build
   ```

   Первый запуск занимает несколько минут.
3. Откройте сайт: http://localhost:80. Сервер отвечает на http://localhost:3000, документация API (Swagger) — на http://localhost:3000/docs.
4. Создайте первого администратора: сначала зарегистрируйтесь запросом (`curl -X POST http://localhost:3000/auth/register -H "content-type: application/json" -d '{"email":"you@example.com","password":"длинный-пароль"}'`), затем выдайте права:

   ```bash
   docker compose exec db psql -U app -d app -c "UPDATE \"Account\" SET role='admin' WHERE email='you@example.com';"
   ```

   После этого войдите на http://localhost:80/login.
5. Остановить: `Ctrl+C`. Повторный `docker compose up` запустит всё снова, данные сохранятся.

Если что-то не работает, выполните `docker compose logs`. Порты и пароль базы меняются переменными `FRONTEND_PORT`, `BACKEND_PORT`, `POSTGRES_PASSWORD`.

## Остальные части

Бот, мобильное приложение и десктоп в `docker compose` не входят. Им нужен запущенный сервер.

**Telegram-бот**

```bash
cd telegram
cp .env.example .env     # впишите BOT_TOKEN от @BotFather; API_URL указывает на сервер; API_KEY сервером больше не проверяется
npm install
npm run start:dev
```

**Мобильное приложение**

```bash
cd mobile
npm install
npm start                # откроется Expo
```

Адрес сервера задан в `mobile/api/client.ts` (`API_URL`). Для эмулятора Android это `http://10.0.2.2:3000`, для телефона — адрес компьютера в вашей сети.

**Десктоп**

```bash
cd desktop
npm install
npm run dev
```

Сборка установщика: `npm run dist`.

**Сайт без Docker**

```bash
cd frontend
npm install
npm run dev
```

Адрес сервера задаётся переменной `VITE_API_URL` (по умолчанию `http://localhost:3000`, см. `frontend/.env.example`).

**Облачные серверы**

В `infrastructure/` лежат файлы Terraform. Прочитайте их и проверьте через `terraform validate`, прежде чем применять.

## API

Полное описание и пробные запросы — в Swagger: `/docs` на сервере. Кратко:

| Ресурс | Без входа | Администратор (cookie сессии) |
|---|---|---|
| `/services` | `GET /services`, `GET /services/:id` | `POST`, `PUT /:id`, `DELETE /:id` |
| `/masters` | `GET /masters`, `GET /masters/:id` | `POST`, `PUT /:id`, `DELETE /:id` |
| `/clients` | ничего | всё |
| `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout` | да | да |
| `/bookings` | `POST /bookings` (заголовок `Idempotency-Key` защищает от повтора) | `GET`, `GET /:id`, `PUT`/`PATCH /:id`, `DELETE /:id`, `GET /busy` (занятое время), `GET /:id/transitions` (допустимые статусы) |
| `/notices` | ничего | всё |
| `/booking-status-logs`, `/booking-audit-logs` | ничего | чтение (история статусов и журнал изменений) |

Запрос на изменение данных с cookie должен нести заголовок `X-Requested-With` (защита от подделки запросов; сайт его добавляет). Вместо cookie можно отправить `Authorization: Bearer <token>` из ответа `/auth/login`. Список поддерживает параметры `q` (поиск), `sort`, `offset`, `limit`. Частота запросов ограничена: `RATE_LIMIT_MAX` в минуту с одного адреса (по умолчанию 100).

## Куда писать свой код

Рядом с каждым сервисом сервера лежит файл `*.hooks.ts` (например, `backend/src/booking-service/booking-service.hooks.ts`). Он создан пустым, и повторная генерация в Engine его **не перезаписывает**. Хуки выполняются до и после методов сервиса: в `before` можно отказать в вызове (например, если слот занят), в `after` изменить ответ. Здесь же добавляются напоминания и уведомления. В этом проекте файлы хуков пустые: правила записи (рабочие часы, пересечения, статусы, лимит, целостность, журнал, уведомления) генерируются блоками логики в файлы `*.logic.ts` и при повторной генерации обновляются. Своё поведение пишите в хуках, а изменить правила выше проще в `project.json` через Engine.

Всё остальное — обычный код проекта: его можно открыть в любой среде, закоммитить в Git и развивать дальше без Engine.

## Откуда это взялось

Проект собран в редакторе FxM Engine из блоков и сгенерирован нажатием кнопки «Сгенерировать». Правила записи заданы блоками логики в `project.json`, а не написаны руками. Сгенерированные файлы почти не правились: подписи полей, тексты и подключение команды `/services` к API тоже заданы свойствами блоков. **Исключение: три правки в сгенерированных тестах**, потому что генератор пока пишет к ним неподходящие заглушки: в `booking-service.service.test.ts` добавлена заглушка журнала для трёх дополнительных репозиториев и дата записи в рабочее время (`2030-07-01T09:00:00.000Z`); в `booking-service.logic.test.ts` заглушка `updateBooking` в тесте истории возвращает новый объект, а не меняет строку; в `list-query.test.ts` добавлено `filters: {}`. Повторная генерация эти правки перезапишет. Добавлены ещё этот README и `.gitignore`, а файл сборки перенесён из `cicd/.github/workflows/` в `.github/workflows/`, где его ждёт GitHub. Это образец, который мы сделали сами для демонстрации, а не проект клиента.
