# Booking Desk

[![CI](https://github.com/fxm-inteligence/Engine-booking-desk/actions/workflows/build.yml/badge.svg)](https://github.com/fxm-inteligence/Engine-booking-desk/actions/workflows/build.yml)

Образец большого проекта, сгенерированного в FxM Engine: **правила записи заданы блоками бизнес-логики на холсте** (проверка слотов, переходы статусов, целостность, уведомления), а не написаны руками. Онлайн-запись клиентов для сервисного бизнеса (салон, барбершоп, студия). Он показывает, что Engine собирает не отдельные куски, а все части продукта сразу, и даёт оценить код до регистрации и оплаты.

> Собрано в [FxM Engine](https://engine.fxm-int.space). В «Новом проекте» есть галерея из 27 готовых заготовок: сайты, магазины, запись и бронирование, боты, системы для бизнеса. Из любой можно начать свой проект и забрать код в Git.

Это **каркас, а не готовый продукт**. Раздел «Чего здесь нет» ниже стоит прочитать до того, как вы начнёте сравнивать с готовыми сервисами записи.

## Что внутри

Все восемь разделов Engine в одном репозитории:

| Часть | Папка | Технологии | Что это |
|---|---|---|---|

| Сервер | `backend/` | NestJS | CRUD по ресурсам `Service`, `Master`, `Client`, `Booking`, `Notice`; правила записи, вход и роли, Swagger, ограничение частоты запросов |

| Telegram-бот | `telegram/` | Telegraf | Команды `/start`, `/services`, `/book` (диалог: услуга → мастер → день → время), `/mybookings` и клиент для API |

| Сборка и выпуск | `.github/workflows/` | GitHub Actions | Сборка и тесты всех частей на каждый push в `main` |

## Что работает сейчас

Только то, что генератор подключает сам. Остальное — заготовки (см. следующий раздел).

- **Сервер.** Создание, чтение, изменение и удаление услуг, мастеров, клиентов и записей. **Правила записи** задают блоки бизнес-логики на холсте (`project.json`), код выпускает генератор (`booking-service.logic.ts`, `master-service.logic.ts`, `service-service.logic.ts`):
  - *Проверка слотов (Slot Check):* мастер не может иметь две пересекающиеся записи, длительность берётся из услуги (`durationMinutes`), ответ 409; отменённая запись освобождает время. **Рабочие часы:** по умолчанию пн–пт 10:00–20:00, сб 10:00–18:00, воскресенье выходной; **у каждого мастера свой график**: поля `workHours` («tue 14:00-16:00; sat 10:00-14:00», перерывы пишутся через пробел) и `daysOff` («2030-07-01..2030-07-14, 12-31», отпуск или выходные) в таблице мастеров, а если поле пусто, действует график салона. Часовой пояс `Europe/Moscow` общий, в праздники (1–8 января, 23 февраля, 8 марта, 1 и 9 мая, 12 июня, 4 ноября) запись не принимается; запись должна целиком уместиться в рабочее время (ответ 409 «Салон в это время закрыт»). Две записи на одно время, пришедшие одновременно, не пройдут обе (блокировка на PostgreSQL).
  - *Статусы (Status Flow):* `new → confirmed → done`, отменить можно из `new` и `confirmed`; недопустимый переход отвечает 409; каждый переход сохраняется в историю (`GET /booking-status-logs`); запись, которую не подтвердили за 24 часа, сама отменяется (таймер).
  - *Целостность (Integrity):* услугу или мастера с записями удалить нельзя (409).
  - *Лимит (Limit):* не больше трёх записей на один телефон на один день (защита публичной формы от спама).
  - *Идемпотентность:* повтор `POST /bookings` с тем же заголовком `Idempotency-Key` не создаёт вторую запись.
  - *Журнал (Audit):* кто и что менял в записях (`GET /booking-audit-logs`).
  - *Уведомления (Reaction):* новая запись и подтверждённая запись за 24 часа до начала создают запись в таблице `Notice` («новая запись», «напомнить клиенту»): это ящик уведомлений для персонала (`GET /notices`, страница `/notices`). Писем и сообщений клиенту сервер не отправляет, см. следующий раздел.
  - *Доступные маршруты:* `GET /bookings/busy` (занятое время, **открыт всем и без имён и телефонов**: только границы занятых промежутков), `GET /bookings/free?masterId=…&date=YYYY-MM-DD&lengthKey=<id услуги>` (свободные начала записи на день с шагом 30 минут: график мастера, занятое время и длительность услуги учтены; открыт всем), `GET /bookings/:id/transitions` (в какие статусы запись может перейти сейчас), `PATCH /bookings/:id` (частичное изменение, например только статуса).
  - *Сообщения клиенту в Telegram (Reaction + Messenger):* когда запись подтверждают, клиенту в Telegram уходит «Ваша запись подтверждена…»; за 24 часа до начала подтверждённой записи уходит напоминание (отдельная отметка `tgRemindedAt`). Сообщение идёт на чат из поля `clientTelegramId`, которое заполняет бот; у записи с сайта этого поля нет, и сообщение не отправляется (запись при этом подтверждается как обычно). Сервер нужно запустить с `TELEGRAM_BOT_TOKEN` (токен от @BotFather); `TELEGRAM_API_URL` по умолчанию указывает на Telegram.
  - *Журнал запросов:* сервер пишет по строке JSON на запрос в стандартный вывод (блок «Logging», уровень задаёт `LOG_LEVEL`).

  **Вход и роли** (генерирует блок «Auth»): `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`; сервер выдаёт сессию в защищённом cookie. Регистрация всегда создаёт роль `user`: поле `role` из запроса игнорируется (проверено: `{"role":"admin"}` даёт `user`). Клиент может создать запись без входа (`POST /bookings`), услуги и мастера читаются без входа; всё остальное (изменение услуг и мастеров, список клиентов и записей) доступно только роли `admin`, остальным отвечает 401 или 403. Первого администратора назначает владелец вручную, см. быстрый старт.
- **Сайт.** Публичные страницы: «Услуги» (`/`) и «Мастера» (`/masters`) показывают таблицы с сервера; «Записаться» (`/book`) — форма с выпадающими списками «Услуга» и «Мастер» (берутся из базы), именем, телефоном и временем, над формой календарь занятости на 14 дней (блок «Busy Calendar»: клиент видит занятое время до отправки формы); статус новой записи сервер ставит сам (`new`). Страница входа `/login`. Страницы для сотрудников требуют входа (без сессии браузер уходит на `/login`): «Записи» (`/bookings`) показывает таблицу записей (в каждой строке ссылка «Открыть») и календарь занятости на ближайшие 14 дней (время считает сервер), страница записи (`/bookings/:id`) показывает кнопки статусов (блок «Status Buttons»): только те переходы, которые сервер сейчас разрешает, отказ сервера виден под кнопками, «Уведомления» (`/notices`) и «Клиенты» (`/clients`) показывают таблицы; на страницах есть кнопка «Выйти» и ссылки на соседние страницы сотрудника.
- **Telegram-бот.** `/services` отвечает списком услуг из базы. `/book` ведёт по шагам: услуга → мастер → день (сегодня, завтра, послезавтра) → свободное время (кнопки из `/bookings/free` с учётом графика мастера и длительности услуги); выбор хранится в сессиях бота, последнее нажатие создаёт запись (`clientName` = «Telegram <id>», `clientPhone` = «tg:<id>», `clientTelegramId` = id отправителя). Клиент получает сообщения о подтверждении и напоминание от сервера (см. выше). `/start` приветствует, `/mybookings` честно отвечает, что список записей в боте недоступен (см. следующий раздел).
- **Мобильное приложение и десктоп.** Запускаются и показывают заготовки: экран с заголовком и кнопкой, окно с заголовком и кнопкой.

## Что проверено

- `cd backend && npm install && npm test`: **108 тестов, все проходят, база данных не нужна**: тесты сервисов (создание, список, чтение, изменение, удаление, 404), разбор параметров списка и тесты, которые генератор пишет к каждому блоку логики (рабочие часы и часовые пояса, пересечения, переходы статусов, история, таймеры, журнал, лимит, идемпотентность, реакции, целостность). Тесты работают на репозитории в памяти.
- **Правила на настоящей базе** (PostgreSQL 16 в Docker, собранный сервер, 34 проверки скриптом по HTTP; скрипт в репозиторий не входит и в CI не запускается): запись в рабочее время создаётся, воскресенье, время после закрытия и праздник отвечают 409, пересекающаяся запись отвечает 409, а запись следом принимается; услуга на 90 минут занимает и второй час; четвёртая запись на один телефон в один день отвечает 409; повтор с тем же `Idempotency-Key` возвращает ту же запись; `new → done` отвечает 409, `new → confirmed` проходит; отменённая запись освобождает время; история статусов и журнал изменений ведутся; услугу и мастера с записями удалить нельзя; новые записи появляются в уведомлениях; уведомления и список записей без входа недоступны, а занятое время и свободные начала доступны без входа и не содержат имён и телефонов; у мастера со своим графиком («вт 14:00–16:00») запись во вторник днём проходит, в среду отвечает 409, в его выходной отвечает 409, а свободные начала на другой вторник лежат в его часах. Telegram проверен против подставного сервера вместо api.telegram.org: подтверждение записи с Telegram-идентификатором отправляет клиенту ровно одно сообщение, подтверждение записи с сайта не отправляет ничего и проходит. Настоящий Telegram и токен BotFather не использовались. Таймер отмены через 24 часа и напоминания за 24 часа (в Telegram и в `Notice`) на живом сервере не ждались: они проверены только тестами.
- **Сайт на живом сервере:** собран (`tsc -b && vite build`). Новые страницы (календарь на `/book`, ссылка в строке таблицы, страница `/bookings/:id` с кнопками статусов) в браузере не открывались, проверена только сборка. Раньше в браузере проверены вход сотрудника, `/bookings` с таблицей и календарём, `/notices`. Playwright-тесты страниц, которые теперь пишет генератор (`frontend/e2e/`), не запускались.
- **GitHub Actions** на каждый push в `main`: собирает сайт, сервер, мобильное приложение (проверка типов), бота и десктоп, затем запускает тесты. Для сайта шаг запускает тесты Playwright (ставит браузер Chromium), для бота `npm test`. Результат виден в значке выше и во вкладке Actions.
- **Сквозная проверка вручную в Docker** (не входит в CI): `docker compose up --build` поднимает базу, сервер и сайт; публичные маршруты отвечают 200, защищённые отвечают 401 без входа и 403 для обычного пользователя, 200 для администратора; регистрация с `role: admin` создаёт `user`; неверный пароль даёт 401; в настоящем браузере проверен весь путь: гость на `/bookings` уходит на `/login`, форма записи сохраняет запись, вход ведёт на `/bookings` с таблицей, «Выйти» снимает сессию; пересекающаяся запись у того же мастера отвечает 409, запись встык принимается (проверено на 30-минутной услуге). Смена статуса через `PATCH` проверена скриптом по HTTP (см. выше). Диалог `/book` собирается (`tsc`), его адреса проверены по HTTP (`/services`, `/masters`, `/bookings/free`), но сам бот не запускался ни с подставным клиентом, ни с токеном BotFather.

## Чего здесь нет

Честный список, чтобы вы не нашли это сами и не разочаровались:

- **Письма и SMS не подключены, Telegram-сообщения работают только для записей, сделанных через бота.** Персонал видит «новая запись» и «напомнить клиенту» в ящике `Notice`. Клиенту с сайта сообщение не уходит: у него нет Telegram-идентификатора. Мастеру в Telegram ничего не отправляется. Оплаты нет.
- **Расписание: график и выходные мастеров есть, остальное общее.** Часовой пояс и праздники (российские государственные, перенесённые выходные не учтены) общие для салона. График мастера записывается строкой и формой не проверяется: опечатка в `workHours` оставит мастера без часов, то есть недоступным, а не откроет запись. Проверка занятости читает все записи мастера (поиском по полю), она не рассчитана на миллионы записей. Если длительность услуги не нашлась (нет базы, неизвестный id), берётся 60 минут. Срок автоотмены (24 часа) и срок напоминания заданы в блоках, их можно переопределить переменными `FLOW_BOOKING_STEPS_NEW_TO_CANCELLED_AFTER` и `REACTION_BOOKING_REMINDER_NOTICE_BEFORE`.
- **Бот не знает, чьи записи у собеседника.** `/mybookings` отвечает фиксированным текстом: список записей закрыт для посторонних, а бот ходит без входа, поэтому «мои записи» показать нельзя, не раскрыв чужие. Бот записывает клиента как «Telegram <id>» с телефоном «tg:<id>» (имя и телефон в диалоге не спрашиваются). Бот ходит только в публичные маршруты (услуги, мастера, свободное время, создание записи); общий ключ `API_KEY` сервером не поддерживается. У мобильного экрана и десктопного окна нет списка записей. Клиент для API у мобильного приложения сгенерирован (`mobile/api`), но ни к одной кнопке не привязан. У десктопа клиента для API нет.
- **Вход есть только на сайте.** Мобильное приложение и десктоп не умеют входить (экран входа не нарисован), бот не связывает Telegram с аккаунтом. Клиенты бота и мобильного всё ещё могут отправлять заголовок `x-api-key`, но сервер его больше не проверяет.
- **Роли и вход минимальны.** Две роли (`user` и `admin`), свободная регистрация (любой может создать обычную учётную запись, она ничего не открывает), нет подтверждения почты, сброса пароля и интерфейса для выдачи прав: администратора назначают SQL-командой. Токен сессии хранится в cookie, `JWT_SECRET` должен быть длинным случайным значением.
- **Тесты сервера на репозитории в памяти.** У мобильного приложения и десктопа тестов нет. Тесты бота (`telegram/`, 6 штук, запущены: 6 из 6) не касаются Telegram и сети: они проверяют, что каждая команда зарегистрирована и отвечает и что форматирование ответов API верное; диалог записи кнопками они не проходят. Тесты сайта (Playwright, 7 страниц, запущены: 7 из 7) открывают страницы, проверяют их содержимое и переход к входу; запись в них не оформляется. Проверка на настоящей базе по HTTP сделана вручную скриптом, в репозиторий и CI она не входит.
- **Мобильное приложение проверено только типами**, на телефоне и в эмуляторе оно не запускалось.
- **Десктоп собирается, но окно не запускалось** и установщик (`npm run dist`) не проверялся.
- **Terraform проверен только `terraform validate`** (Terraform 1.9, провайдер AWS 5.100: «The configuration is valid»). `plan` и `apply` не запускались и к реальному аккаунту не применялись. Перед `apply` проверьте регион, образ контейнера и стоимость.
- **Сайт на React + Vite, а не на Next.js.** Десктопное приложение Engine собирается только поверх такого сайта, а в одном проекте они должны сочетаться.

## Быстрый старт: сайт, сервер и база

Нужен [Docker Desktop](https://www.docker.com/products/docker-desktop/) (бесплатный).

1. Скопируйте `backend/.env.example` в `backend/.env` и впишите в `JWT_SECRET` длинный случайный текст (подпись сессий). Без него вход не работает. При запуске по `https` поставьте `COOKIE_SECURE=true`.
2. В корне репозитория выполните:

   ```bash
   docker compose up --build
   ```

   Первый запуск занимает несколько минут.
3. Откройте сайт: http://localhost:80. Сервер отвечает на http://localhost:3000, документация API (Swagger) — на http://localhost:3000/docs.
4. Создайте первого администратора: сначала зарегистрируйтесь запросом (`curl -X POST http://localhost:3000/auth/register -H "content-type: application/json" -d '{"email":"you@example.com","password":"длинный-пароль"}'`), затем выдайте права:

   ```bash
   docker compose exec db psql -U app -d app -c "UPDATE \"Account\" SET role='admin' WHERE email='you@example.com';"
   ```

   После этого войдите на http://localhost:80/login.
5. Остановить: `Ctrl+C`. Повторный `docker compose up` запустит всё снова, данные сохранятся.

Если что-то не работает, выполните `docker compose logs`. Порты и пароль базы меняются переменными `FRONTEND_PORT`, `BACKEND_PORT`, `POSTGRES_PASSWORD`.

```bash
cd telegram
cp .env.example .env     # впишите BOT_TOKEN от @BotFather; API_URL указывает на сервер; API_KEY сервером больше не проверяется
npm install
npm run start:dev
```

```bash
cd mobile
npm install
```

## API

Полное описание и пробные запросы — в Swagger: `/docs` на сервере. Кратко:

| Ресурс | Без входа | Администратор (cookie сессии) |
|---|---|---|
| `/services` | `GET /services`, `GET /services/:id` | `POST`, `PUT /:id`, `DELETE /:id` |
| `/masters` | `GET /masters`, `GET /masters/:id` | `POST`, `PUT /:id`, `DELETE /:id` |
| `/clients` | ничего | всё |
| `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout` | да | да |
| `/bookings` | `POST /bookings` (заголовок `Idempotency-Key` защищает от повтора) | `GET`, `GET /:id`, `PUT`/`PATCH /:id`, `DELETE /:id`, `GET /busy` (занятое время), `GET /:id/transitions` (допустимые статусы) |
| `/notices` | ничего | всё |
| `/booking-status-logs`, `/booking-audit-logs` | ничего | чтение (история статусов и журнал изменений) |

Запрос на изменение данных с cookie должен нести заголовок `X-Requested-With` (защита от подделки запросов; сайт его добавляет). Вместо cookie можно отправить `Authorization: Bearer <token>` из ответа `/auth/login`. Список поддерживает параметры `q` (поиск), `sort`, `offset`, `limit`. Частота запросов ограничена: `RATE_LIMIT_MAX` в минуту с одного адреса (по умолчанию 100).

## Куда писать свой код

Рядом с каждым сервисом сервера лежит файл `*.hooks.ts` (например, `backend/src/booking-service/booking-service.hooks.ts`). Он создан пустым, и повторная генерация в Engine его **не перезаписывает**. Хуки выполняются до и после методов сервиса: в `before` можно отказать в вызове (например, если слот занят), в `after` изменить ответ. Здесь же добавляются напоминания и уведомления. В этом проекте файлы хуков пустые: правила записи (рабочие часы, пересечения, статусы, лимит, целостность, журнал, уведомления) генерируются блоками логики в файлы `*.logic.ts` и при повторной генерации обновляются. Своё поведение пишите в хуках, а изменить правила выше проще в `project.json` через Engine.

Всё остальное — обычный код проекта: его можно открыть в любой среде, закоммитить в Git и развивать дальше без Engine.

## Откуда это взялось

Проект собран в редакторе FxM Engine из блоков и сгенерирован нажатием кнопки «Сгенерировать». Правила записи заданы блоками логики в `project.json`, а не написаны руками. Сгенерированные файлы почти не правились: подписи полей, тексты и подключение команды `/services` к API тоже заданы свойствами блоков. Проект пересобран 11 ноября 2026 новым генератором (график мастеров из таблицы, открытые маршруты занятости и свободного времени, страница записи с кнопками статусов, диалог бота, журнал запросов). **Исключение: одна правка в сгенерированном файле.** В `booking-service.service.test.ts` (его пишет не нынешний, а прежний генератор: сервис с несколькими зависимостями теперь остаётся без такого теста) конструктору сервиса передан ещё один аргумент-заглушка, для Telegram. Повторная генерация этот файл не трогает. Добавлены ещё этот README и `.gitignore`, а файл сборки перенесён из `cicd/.github/workflows/` в `.github/workflows/`, где его ждёт GitHub. Это образец, который мы сделали сами для демонстрации, а не проект клиента.
